# 为什么 cove 用 Go，而不是其他主流语言

> 一个语言选型问题，回答的不是「Go 好不好」，而是「在 cove 的约束下，Go 是不是总成本最低」。
> 本文把约束摆到台面上，逐语言对比，也把 Go 的短板写清楚——不吹。

---

## 0. 先明确约束，语言是为约束服务的

cove 不是一个「用什么语言都能写」的玩具，它的约束是硬的：

| 约束 | 含义 |
|------|------|
| 单人/极小团队长期维护 | 代码库已有约 960 个 Go 文件（其中约 350 个非测试）、几十个工具、多个后台任务，重构时必须有编译器兜底 |
| 下载即用 | 用户不能先装 Python 环境、Node 运行时、JRE |
| 单文件分发 | 一个二进制文件跑 Windows / macOS / Linux，最好还交叉编译无坑 |
| 重度并发 | 多工具并行调用、子 agent、流式 SSE 输出、后台 dream 整理同时跑 |
| 顺带的通用自动化 | 本质是代码助手，但也要能执行 shell/PowerShell、headless 浏览器、网页抓取/搜索、MCP，顺带操作电脑 |
| 长驻 + 高频 I/O | 频繁读写文件、执行 shell、网络请求、Git 操作 |

把「单文件 × 跨平台 × 并发 × 单人长期维护」这几个条件叠起来，候选语言一个个都会被某个约束淘汰。下面逐个过。

---

## 1. 逐语言对比

### Python —— AI 生态最强，但「分发」这一关直接出局

**优势**：LLM 生态全球第一（`openai` / `anthropic` / `litellm` / `langchain` 全是 Python 一等公民），写原型最快。

**为什么不适合 cove**：

- **分发地狱**：虚拟环境、`pip` 依赖、版本冲突。用户「下载一个文件就能跑」这个核心卖点，用 Python 几乎不可能优雅实现。
- **GIL 削弱真并发**：agent 要并行跑多个工具、流式处理多个子任务，`asyncio` 能绕但心智负担重，且一旦混入同步库就串行。
- **打包器不可靠**：`PyInstaller` 体积大、启动慢、**经常被杀毒软件误报**——这对一个要用户装到本机、还要执行 shell 的工具是致命的信任问题。
- **类型弱**：`dict[str, Any]` 满屏飞，单人维护 600 文件的库会崩。`mypy` 是补救，不是保障。

**结论**：做「给自己用的实验」用 Python 最快；做「给别人用的终端工具」Python 是最差选择之一。

---

### Node.js / TypeScript —— 能做，但「零依赖单文件」要付出额外代价

**优势**：TS 类型不错、npm 生态大、异步/流式是原生心智，Claude Code 本身就是 Node 写的，证明这条路可行。

**为什么 cove 没选**：

- **需要运行时**：分发要么要求用户装 Node，要么用 `pkg` / `bun build` 打包成单文件——后者在 native 模块、动态 `require`、跨平台上有各种坑，不是「一行交叉编译」那么省心。
- **单线程模型**：`worker_threads` 比 goroutine 笨重，进程内存和启动速度都不如 Go 的静态二进制。
- **依赖树深**：`node_modules` 动辄几百个包，供应链攻击面大；对一个要拿用户 API key、要执行 shell 的工具，依赖越少越可信。

**结论**：Node 完全能做出好 CLI，但「零依赖单文件 + 低启动延迟 + 低内存」这三个卖点，Go 是天生的，Node 是后天拼出来的。

---

### Rust —— 性能和内存安全的天花板，但「生产力」代价不适合单人快推

**优势**：和 Go 一样能出单文件静态二进制，性能更强、内存更省、无 GC，终端 UI 生态（`ratatui`）比 Go 成熟。

**为什么不选**：

- **开发速度慢**：borrow checker + 生命周期标注，让「快速试错、大量堆功能」的 agent 项目迭代明显变慢。
- **编译慢**：改一处等编译，对需要频繁验证的行为很伤。
- **LLM/MCP SDK 生态弱**：和 Python/TS 比差一截，很多客户端要自己写。

**结论**：Rust 是 Go 最强的竞品。如果 cove 的目标是「极致性能的终端 UI」或「库给别的程序用」，Rust 更优；但 cove 的目标是「一个人快速、长期维护一个功能很全的 agent」，Rust 的生产力代价不划算。

---

### Java / Kotlin —— Android 原生但 CLI 是短板

**优势**：Kotlin 语法现代，JVM 生态成熟，Android 是 Kotlin 的主场。

**为什么不适合**：

- **CLI 冷启动慢、内存大**：JVM 启动要几百毫秒到秒级，常驻内存几十 MB 起步。
- **分发要 JRE**：除非上 GraalVM native-image，但 native-image 的反射/配置复杂度高，交叉编译也远不如 Go 顺。

**结论**：Android 很强、CLI 弱，而 cove 的主战场是 CLI。

---

### C / C++ —— 排除

性能天花板，但开发效率、内存安全、交叉编译、依赖管理每一项对单人项目都是劝退。不做无谓讨论。

---

## 2. Go 具体帮 cove 解决了什么（结合真实代码）

1. **单文件静态二进制 + 零交叉编译坑**
   `GOOS=windows GOARCH=arm64 go build` 一条命令出六平台产物。没有运行时依赖 = 少一层攻击面 = 用户更敢装。这是 cove「下载即用」这个卖点的物理基础。

2. **启动快、内存省**
   CLI 冷启动在百毫秒内，常驻 agent 内存可控，适合 `cove -p` 这类一次性调用和长驻 REPL 两种形态。

3. **goroutine + channel 天然契合 agent 的并发模型**
   工具并行调用、子 agent 生成、SSE 流式解析、后台 dream 整理，都用 goroutine 表达得自然；`context` 统一做取消/超时/上限，`sync.WaitGroup`/`errgroup` 收拢并发错误。这套并发心智对「一个 agent 同时干多件事」是刚需。

4. **强类型 + 编译期检查 = 单人可长期维护**
   几十个工具的 JSON schema、配置、消息结构，重构时编译器全程兜底。这是单人项目能活到 v12 而不是重构崩溃的关键。

5. **标准库够用，第三方依赖少**
   `net/http`、`encoding/json`、`os/exec`、`io`、`context`、`bufio` 覆盖了大部分需求，MCP/SSE/WebSocket 客户端自己写也不难。依赖少 = 供应链风险小 = 更可信。

---

## 3. 诚实说 Go 的短板（不是没有代价）

1. **错误处理啰嗦**：`if err != nil` 让代码行数膨胀，读起来有噪音。
2. **泛型来得晚、能力弱**：做「通用工具层」时经常要写重复代码或用 `interface{}` + 断言，不如 TS/Rust 顺。
3. **LLM / MCP 生态不如 Python/TS**：很多 SDK 要自己写或依赖维护不活跃的库，早期踩过不少坑。
4. **终端 UI 生态一般**：`bubbletea` 可用但不如 `ratatui`（Rust）/`ink`（Node）成熟，cove 后来自己写了 `internal/termui`。
5. **JSON 动态结构不直观**：处理工具 schema 这种 `map[string]any` 场景，比 TS 啰嗦。

这些都是真实代价，但**每一项都可以用「多写一点代码」解决**；而 Python 的分发、Node 的运行时、Rust 的编译速度，是**没法用「多写一点代码」解决的**。这就是关键区别。

---

## 4. 结论

| 如果你的首要目标是… | 选 |
|---|---|
| 最快做出 demo / 用最全的 LLM 生态 | Python |
| 和 JS 生态无缝、团队全是前端 | TypeScript |
| 极致性能、内存安全、好终端 UI | Rust |
| **单文件分发 × 跨平台 × 重度并发 × 单人长期维护 × 移动端复用** | **Go** |

cove 的选择不是「Go 是最棒的语言」，而是「**在 cove 的约束组合下，Go 是妥协最少、总成本最低的语言**」。

它牺牲了生态丰富度和语言表达力，换来了分发、并发、可维护性和移动端复用这四个对 cove 生死攸关的能力。这四样，恰恰是一个「要长期演进、到处能跑、并发密集的 agent」最需要的。
